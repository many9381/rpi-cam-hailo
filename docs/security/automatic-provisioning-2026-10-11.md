# 앱 초기 설정과 자동 실행 — 2026-10-11

> Privacy: Device/client addresses in this report are documentation-only
> examples. Original local measurements are retained outside Git.

대상은 상위 `yocto-rpi5-cam-firmware` 저장소의 카메라 이미지와 SSD 설치 절차다.
기존 앱의 TLS·인증·무결성 검사와 웹 초기 설정 절차를 유지한다.

## 구성

- 호스트의 Git 제외 경로 `keys/camera-firmware/`에 Ed25519 서명 키를 한 번
  생성한다. 디렉토리 권한은 `0700`, 개인키는 `0600`이다. 레시피는 공개키만
  입력으로 받아 바이너리에 포함하고, 이미지와 산출물에 공개키 사본을 남긴다.
- `scripts/install-ssd.sh`는 SSD 삭제 전에 로컬 개인키와 선택한 이미지의
  공개키를 대조한다. 이미지 기록 후 장비별 TLS 키·자체 서명 인증서와 임의의
  30바이트 SRTP 세션 키를 생성한다. 인증서의 SAN에는 로컬 `public_host`를 넣는다.
- 실제 설치된 바이너리, 최종 `app.yaml`, 부팅 파티션의 `kernel_2712.img`를
  SHA-256으로 해시하고 manifest 원문을 Ed25519로 서명한다. 개인키는 호스트에서만
  사용하며 임시 사본은 설치 스크립트의 기존 비공개 임시 디렉토리와 함께 정리한다.
- TLS 인증서·키는 앱의 파일 검증 요구에 맞춰 서비스 UID 소유로 설치한다.
  설정·manifest·서명은 root와 서비스 그룹으로 제한한다. 모든 선행 파일을 쓴 뒤
  활성 설정을 원자적으로 게시하고, SSD를 읽기 전용으로 다시 마운트해 검증한다.
- 앱 서비스는 `/boot` 마운트 후 자동 시작한다. 첫 웹 설정에서 운영자가 영구
  관리자와 접근 IP를 등록한다. 앱의 `BootstrapService`가 같은 과정에서 RTSP
  Digest 인증 파일을 생성하므로 설치 스크립트는 공통 관리자 암호나 별도 계정을
  주입하지 않는다. 초기 설정 전 영상 실행을 제한하는 기존 동작도 유지한다.

## 경계와 운영

일반 WIC와 빌드 캐시에는 장비별 TLS/SRTP 비밀값이나 개인 서명 키를 넣지 않는다.
표준 설치 스크립트가 SSD를 장비별로 준비한다. 다른 도구로 WIC만 기록하면 실제
`app.yaml`이 없으므로 서비스는 비활성 상태다. 과거의 개발 공개키로 빌드된
이미지에는 새 개인키로 서명할 수 없으며 이미지 재빌드가 필요하다.

개발용 TLS 인증서는 자체 서명이며 유효기간은 365일이다. 브라우저 신뢰 등록과
만료 전 교체는 운영 작업이다. 공인 인증서나 자동 갱신을 제공한다고 주장하지 않는다.
서명 대상 바이너리·기본 설정·커널 변경 시 재서명한다. 앱의 런타임 설정 저장소는
기존 경로를 유지한다. 재부팅은 계정과 설정을 보존하지만 재설치는 새 초기 설정이다.

## 검증

호스트 시험은 실제 OpenSSL로 인증서·서명을 생성하고 독립 서명 검증, 키 불일치,
커널/설정 변조, 권한, 경로 탈출, 잘못된 빌드·마운트, 설치 반복 및 서명 실패 시
활성 설정 미게시를 검사한다. 설치 함수의 읽기 전용 재검증 실패도 성공으로
처리하지 않는지 확인한다.

검증 결과:

- 호스트 전체 시험 **286개 통과**. 이 중 초기 설정 시험 11개는 실제 OpenSSL을
  사용한다. 긴 DNS 이름의 X.509 CN 길이 제한 문제는 짧은 고정 CN과 전체 SAN으로
  수정했고, 수정 전 실패 및 수정 후 `openssl verify -verify_hostname` 성공을 확인했다.
- Yocto Hailo 카메라 이미지 빌드 **통과**: 총 7,768개 작업, 7,734개 재사용.
  build ID는 `20261011T060311Z-e664cb9647e7`이다. QEMU 이미지는 빌드하지 않았다.
- 최종 rootfs의 공개키와 앱 바이너리 내 공개키가 호스트 공개키와 일치한다.
  서비스 활성화 및 `/boot` 마운트 의존성, 개발용 Git 저장소와 Wi-Fi 수정 유지도
  확인했다. 일반 이미지에 활성 설정과 장비별 TLS 개인키가 없는 것을 확인했다.
- WIC 압축 이미지·bmap·공개키 산출물의 SHA-256 **통과**. 수집된 공개키와
  로컬 개인키의 대응 검사도 **통과**했다.
- 독립 코드 검토와 shell 문법·Python 컴파일·diff 공백 검사 완료.

산출물은 상위 저장소 `artifacts/20261011T060311Z-e664cb9647e7/rpi5-camera-hailo/`,
실행 증거는 Git 제외 경로 `.state/camera-provision-2026-10-11/`에 보관한다.
서명 키·장비 주소 설정도 Git 제외 여부를 확인했다.

위 빌드 검증 시점에는 대상 SSD가 연결되지 않아 새 이미지 설치를 수행하지 않았다.

## 후속 진단: Wi-Fi에서 초기 계정 로그인 실패

2026-10-11 설치 기록과 Wi-Fi 장치의 `/etc/rpi5-build-id`에서 위 빌드가
설치된 것을 확인했다. 앱은 자동 시작되어 초기 계정 화면을 제공했다.
다만 설치 시 `public_host`에 이전 유선 주소 `198.51.100.61`을 사용했고,
실제 브라우저는 Wi-Fi 주소 `198.51.100.60`으로 접속했다.

실기기에서 같은 초기 계정을 사용하고 Origin만 바꿔 비교했다.

| 요청 Origin | 로그인 응답 |
|---|---|
| `https://198.51.100.60:8443` | `403`, `E_REQUEST_ORIGIN` |
| `https://198.51.100.61:8443` | `200`, 초기 계정 역할 `viewer` |

비밀번호 오류가 아니라 `SecurityRequestGate`의 Origin 검사 실패다.
`LoginPage`는 이 오류도 일반 자격 증명 실패 문구로 표시한다.
진단에 사용한 세션은 즉시 로그아웃했으며 초기 관리자 등록은 진행하지 않았다.
초기 암호와 세션 쿠키는 출력하거나 파일에 저장하지 않았다.

호스트의 Git 제외 파일 `keys/camera-firmware/device.json`을
`198.51.100.60`으로 수정하고 기존 서명 키와 이미지 공개키의 일치를 재검증했다.
이는 다음 설치에 적용되는 주소 변경이며 실행 중인 Pi를 갱신하지 않는다.
현재 Pi 계정에는 앱 설정을 쓰거나 서비스를 재시작할 권한이 없으므로,
SSD를 PC에 연결한 후 설정·TLS 인증서·manifest 서명을 함께 갱신해야 한다.
주소만 변경하는 작업에는 이미지 재빌드가 필요하지 않다. `app.yaml`만 직접
수정하면 무결성 검증이 실패하므로 서명 갱신을 생략하지 않는다.
기존 계정·런타임 설정·SRTP 키는 주소 보정 과정에서 보존한다.

진단 증거는 상위 저장소의 Git 제외 경로
`.state/camera-origin-2026-10-11/diagnosis.json`에 기록했다.
현재 장치의 주소 보정과 Wi-Fi Origin에서의 로그인 재검증은 아직 미완료다.

주소를 매번 고치는 대신 DHCP를 지원하고 접근 IP 제한을 선택 사항으로 바꾸는
후속 수정으로 전환했다. 현재 설계와 검증 범위는
[DHCP 초기 설정 기록](dhcp-setup-2026-10-11.md)을 참고한다. 위 고정 주소 보정
설명은 진단 당시의 조치이며 현재 설계의 필수 설치 조건이 아니다.
