# RTSPS 실기기 보안 회귀 검증 — 2026-10-11

**전체 판정: 미통과.** 설치된 Hailo 이미지에서 정상 Digest 인증과 암호화 영상
수신은 통과했지만, 인증하지 않은 연결이 기존 세션의 영상을 중단시키는 문제를
재현했다. 이 기록은 시험 결과이며 해당 문제의 수정 완료 기록이 아니다.

후속 소스 수정과 별도 프로세스의 Pi 재검증은
[세션 격리 수정 기록](rtsp-session-isolation-remediation-2026-10-11.md)에 이어서 남긴다.
[새 이미지 설치·운영 검증](rtsp-deployment-validation-2026-10-11.md)도 완료했다.
아래 내용과 기존 FAIL 증거는 수정 전 설치 이미지에 대한 기록으로 유지한다.

대상은 `20261011T155422Z-e664cb9647e7` / `rpi5-camera-hailo`, GStreamer
**1.28.8**이다. Wi-Fi로 접속했고 SSH 호스트 키, TLS 공개 인증서, 보드·USB 루트
UUID·빌드 식별자를 고정해 검사했다. 앱과 관련 GStreamer 라이브러리의 장치
SHA-256을 이 이미지의 rootfs와 대조했다. 직접 IP 접속에 따른 인증서 이름
불일치만 예외로 두고 인증서 핀·체인·유효기간을 검사했다.

## 통과한 범위

| 검사 | 관찰 결과 |
| --- | --- |
| TLS·비인증 요청 16개 | TLS 1.3 연결, TLS 포트의 평문 RTSP 거부. Session 헤더 없는 DESCRIBE/SETUP/PLAY/GET_PARAMETER/TEARDOWN은 401이며 SDP·세션을 반환하지 않음. |
| 잘못된 인증 입력 | Basic, MD5, 빈 값·불완전 Digest, 중복 필드·Authorization, 8192바이트 한도 초과, 잘못된 nonce 거부. |
| 정상 인증 및 인증 후 경계 입력 12개 | SHA-256/qop=auth 인증 성공. 같은 Authorization 재전송, 잘못된 비밀값·없는 사용자·위조 nonce·다른 URI·메서드·중복 인증 헤더는 401. |

| 인증 후 KeyMgmt 경계 입력 | 빈 값·빈 따옴표·공백·잘못된 MIKEY 데이터 4개는 SETUP 200으로 무시하고 처리. 각 세션 TEARDOWN 200, 앱 중단 없음. 잘못된 입력을 모두 거부했다는 의미는 아님. |
| 평문 미디어 전환 | 인증된 RTP/AVP/TCP SETUP은 461. RTP/SAVPF/TCP SETUP과 PLAY는 200. |
| 실제 암호화 미디어 | **SRTP 9,261개, SRTCP 3개** 복호화·인증 성공. SDP의 SSRC와 수신 패킷 SSRC 일치. H.264 **1920×1080, 712프레임** 전체 디코딩 성공, ffmpeg 오류 없음. |
| 수신기 인증·재전송 검사 | 실제 수신한 SRTP/SRTCP 각각의 인증 태그 변조는 libsrtp 인증 오류, 동일 패킷 재전송은 replay 오류로 거부. |
| 서버에 보내는 RTCP 경계 입력 | 정상 SRTCP RR/SDES, 재전송, 인증 태그 변조, 평문 RTCP, 인증된 SDES PRIV 길이 오류·SDES 항목 길이 초과를 제한된 횟수로 전송. 이후에도 미디어 수신과 GET_PARAMETER/TEARDOWN 200 유지. |

호스트 수신기는 같은 Yocto 입력의 libsrtp 2.7.0으로 작은 전용 도구를 빌드했다.
SRTP/SRTCP 정상 왕복·태그 변조·재전송 자체 검사 후 실기기 패킷에 사용했다.
SDP 키와 인증 헤더 원문은 저장하지 않았다. 프레임 수는 실제 디코딩 수이며,
원시 H.264에 임의 프레임률을 붙여 MP4 시간 검증으로 바꾸지 않았다.

## 미통과: 비인증 연결이 기존 세션을 정리함

문제 식별자는 이 기록 안에서만 사용하는 **RTSP-SESSION-ISOLATION-01**이다.
CVE 부여나 외부 공개 여부를 조사·판정한 이름이 아니다.

재현 조건은 RTSPS 포트에 연결할 수 있고 **현재 사용 중인 유효한 Session 값을
이미 알고 있는 경우**다. 시험에서 직접 만든 세션만 사용했으며 다른 사용자의
세션 번호를 추측하거나 탐색하지 않았다. 세션 값 탈취 방법이나 원격 코드 실행,
인증 없는 영상 복호화를 입증한 결과도 아니다.

정상 인증으로 SETUP/PLAY한 연결 A를 유지한 뒤, 인증 정보 없는 연결 B에서
A의 Session 값으로 요청하고 B만 닫았다. 결과는 다음과 같다.

| B의 동작 | B 응답 | 이후 A의 미디어와 인증된 요청 |
| --- | --- | --- |
| B 없음 — 정상 대조군 | 해당 없음 | 초당 SRTP 656~667개, PLAY 200 / TEARDOWN 200. |
| 기존 Session으로 PLAY 후 연결 종료 | 401, 응답 본문 없음 | 남은 버퍼 이후 4개 연속 1초 구간에서 미디어 0개. PLAY 404 / TEARDOWN 404. |
| 기존 Session으로 OPTIONS 후 연결 종료 | 200, 응답 본문 없음 | 남은 버퍼 이후 4개 연속 1초 구간에서 미디어 0개. PLAY 404 / TEARDOWN 404. |
| 존재하지 않는 Session으로 PLAY 후 종료 — 대조군 | 454, 응답 본문 없음 | 초당 SRTP 652~695개, PLAY 200 / TEARDOWN 200. |

중단된 세션에서도 GET_PARAMETER는 200이었다. 따라서 프로세스 active 또는
keepalive 200만으로 정상 재생을 판정하면 이 문제를 놓친다. 최초 복합 시험의
실패 기록을 보존하고, 입력을 분리한 대조 시험으로 세션 격리 실패를 확인했다.
암호화·RTCP 시험에서 이 입력을 분리한 것은 해당 항목의 통과 처리 목적이 아니며,
전체 결과는 계속 **FAIL**이다.

### 원인과 수정 대상

실제 빌드에 사용한 `gst-rtsp-server-1.28.8/gst/rtsp-server/rtsp-client.c`에서:

1. `handle_request()`는 Session을 찾은 뒤 `client_watch_session()`으로 현재
   연결의 관리 목록에 먼저 넣는다. 이 호출은 URL 인증 검사보다 앞선다.
2. 그다음 앱의 `GstRtspDigestAuth::Check()`가 PLAY를 401로 거부해도 등록은 남는다.
3. 연결 종료의 `cleanup_session()` / `filter_session_media()`는 그 세션의 TCP
   미디어를 정리한다. 해당 미디어가 원래 다른 연결의 것인지 구분하지 않는다.
4. 앱은 현재 OPTIONS를 인증 없이 허용하므로, 등록을 단순히 URL 인증 검사
   뒤로 옮기는 것만으로는 OPTIONS 경로를 해결할 수 없다.

후속 수정은 **인증 실패·비인증 OPTIONS가 기존 세션에 등록·수명 연장·정리 등의
영향을 주지 않도록 요청 처리 순서를 보완**해야 한다. Session 없는 공개 OPTIONS는
유지할 수 있다. 위 두 실패 경로뿐 아니라 잘못된 Session, 정상 인증 후 세션
처리·재연결·종료를 회귀 검사해야 한다. 관련 변경은 GStreamer Yocto append/patch와
필요한 앱 인증 정책에 함께 반영하고, 새 바이너리로 동일 실기기 시험을 반복해야 한다.

이번 작업에서는 제품 코드·layer·설치 이미지·계정·서비스 설정을 변경하지 않았다.
따라서 **현재 설치 이미지에 이 수정이 적용됐다고 보면 안 된다.**

## 종료 상태와 검증 한계

- 시험 전체에서 같은 boot ID와 앱 PID **1169**를 유지했고 재시작은 **0회**였다.
  세션 문제 뒤 새로 만든 정상 세션은 다시 재생·종료할 수 있었다.
- 최종 HTTPS 화면·JS·CSS·setup API는 200, 초기 설정 완료 유지, 비로그인 AI
  detections API는 401이다. 로그인한 웹 영상·AI 검출 화면을 이번에 다시 본 것은 아니다.
- 서버로 보낸 비정상 RTCP 이후 계속 동작함은 확인했다. 서버 내부의 개별 폐기
  카운터나 SDES 분기 실행은 확인하지 못했으며 해당 경고 로그도 관찰하지 못했다.
  클라이언트의 인증·재전송 거부와 서버의 내부 처리를 같은 증거로 취급하지 않는다.
- UDP 전송, 장시간 부하·퍼징·연결 수 고갈, 모든 보안 공지의 원본 재현 입력,
  브라우저 인증서 신뢰·이름 문제 해결은 이번 범위가 아니다.
- 사용자가 로컬 터미널로 입력한 비밀번호 원문은 저장하지 않았다. SHA-256 HA1은
  비밀번호와 동일하게 민감하게 취급했고 Git 제외 0600 파일로만 사용한 뒤 삭제했다.
  인증 파일·Authorization·원시 SDP·SRTP 키는 보존본에 포함하지 않는다.
