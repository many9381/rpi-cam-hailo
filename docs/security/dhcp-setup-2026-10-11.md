# DHCP 환경의 초기 설정과 선택적 접근 IP 제한 — 2026-10-11

## 원인과 변경

이전 이미지는 설치 시 지정한 `http.public_base_url`과 브라우저 Origin이
다르면 로그인을 거부했다. Pi가 유선에서 Wi-Fi로 이동하거나 DHCP 주소가
바뀌면 비밀번호가 맞아도 `E_REQUEST_ORIGIN`이 발생했고, 웹은 이를 일반
자격 증명 실패로 표시했다. 최초 진단은
[자동 초기 설정 기록](automatic-provisioning-2026-10-11.md)에 남겼다.

- 직접 HTTPS 접속은 서버 소켓의 실제 로컬 주소·포트·TLS 여부로 Origin을
  검증한다. 임의의 `Host`·`X-Forwarded-*` 헤더를 신뢰하지 않는다. 다른
  사이트 Origin과 포트·프로토콜 불일치는 계속 거부한다.
- 고정 주소가 없는 설정은 `http.public_base_url: ''`을 허용한다. 호스트의
  새 `device.json` 기본값은 `{"public_host": null}`이다. 명시적으로 등록한
  HTTPS 주소/DNS 이름은 계속 지원하며 기존 로컬 설정을 자동 덮어쓰지 않는다.
- 새 웹 초기 설정의 IP 제한은 기본적으로 꺼져 있다. 운영자는 관리자 계정과
  비밀번호를 만들고, 필요할 때만 접속하는 PC의 허용 IP를 추가한다. Pi의
  미래 DHCP 주소를 초기 설정에서 미리 등록할 필요가 없다.
- 설정 화면에서 확인한 현재 PC 주소는 초기 설정 세션 검증과 이후 안전한
  제한 활성화를 위해 저장한다. 제한이 꺼져 있으면 그 목록으로 접근을 차단하지 않는다.
- 관리자 화면에서 IP 제한을 켜거나 끌 수 있다. 켤 때 현재 관리자의 주소가
  관리자 허용 목록에 없으면 `E_MANAGEMENT_IP_LOCKOUT`으로 거부한다.
- 로그인 화면은 Origin 오류와 잘못된 자격 증명을 구분해서 안내한다.
  자동 주소 모드의 스트림 URL도 해당 요청의 실제 서버 주소로 표시한다.

## 보존되는 보안 동작과 저장 형식

보안 DB 형식 5를 6으로 올려 IP 제한 활성화 여부를 명시적으로 저장한다.
기존 장비는 제한이 켜진 상태로 이전하므로 업데이트만으로 접근 범위가 넓어지지
않는다. 기존 계정·비밀번호 해시·허용 IP·감사 기록은 보존한다. 과거 지원 형식
2~5도 순차 이전하며, 이전 실패는 트랜잭션으로 되돌린다. 정책 값이 손상되면
로그인·세션 검증을 허용하지 않는다.

정책 변경은 관리자 권한과 최근 인증을 요구한다. 설정 저장·감사 기록·세션
폐기는 한 트랜잭션에서 처리하며, 저장 성공 후 모든 사용자가 다시 로그인한다.
기존 웹/API 호출이 새 초기 설정 필드를 생략하면 종전의 IP 제한을 유지한다.

IP 제한을 꺼도 비밀번호·계정 잠금·역할·세션 만료·관리 재인증·Origin 검사는
유지한다. 세션 쿠키는 로그인한 PC 주소에 묶이며 다른 주소에서 재사용할 수 없다.
계정당 활성 세션 1개 제한도 유지한다. 따라서 **PC 주소가 로그인 도중 바뀌면**
기존 세션이 만료되거나 폐기된 뒤 새로 로그인해야 한다. Pi의 서버 주소 변경과
PC의 세션 주소 변경은 별개다. IP 제한을 끈 상태에서는 인증 화면에 접근할 수 있는
네트워크 주소 범위가 넓어지므로 필요한 장비는 관리자 화면에서 제한을 켠다.

## TLS와 설치 경계

고정 주소 없는 설치의 개발 인증서는 자체 서명이며 SAN은 `camera.local`이다.
이는 이름 확인/DNS 설정을 제공하지 않는다. 직접 IP 접속에서는 브라우저의
인증서 신뢰·이름 불일치 경고가 남을 수 있다. DHCP 변경에도 엄격한 TLS 이름
검증이 필요하면 실제로 해석되는 고정 DNS 이름과 그 이름에 맞는 신뢰 인증서를
사용해야 한다. Origin 검사는 TLS 인증서 신뢰 검사를 대체하지 않는다.

장비별 개인키·인증 정보는 기존 Git 제외 경로를 사용한다. 설정·바이너리·커널의
서명 검증도 유지한다. 기존 SSD를 전체 이미지로 다시 기록하면 계정이 보존되지
않는다. 위 DB 보존 설명은 기존 상태 디렉토리를 유지하는 앱 업데이트에 해당한다.

## 검증과 layer 반영

- 보안 단위 시험: **345개 통과**. 이전 형식·정책 손상·잘못된 비밀번호·다른
  주소의 쿠키 재사용·역할·잠금·만료·정책 저장 실패/되돌리기를 포함한다.
- Origin/설정 시험: **137개 통과**. IPv4/IPv6 실제 소켓 주소 허용, 외부
  Origin·위조 호스트·비 TLS 거부, 새 필드 및 기존 요청 호환성을 확인한다.
- 서비스 단위 시험: **191개 통과**.
- 실제 ServiceApp의 HTTPS 통합 시험: **5개 통과**. 고정 Origin 없는 초기
  로그인/관리자 생성, 위조 헤더 거부, 제한 해제 후 다른 PC 주소의 새 로그인,
  세션 주소 고정, 관리자 차단 방지, 제한 활성화와 세션 폐기를 함께 검증한다.
- 웹 단위 시험: **754개 통과**, 웹 배포 빌드 통과. 브라우저 E2E는 목록 18개를
  확인했으나 이 호스트에 Chromium이 없어 실행하지 않았다.
- 호스트 시험: **287개 통과**. 자동 주소 설치의 TLS 생성과 무결성 서명 검증을 포함한다.

Yocto 이미지 빌드 및 장비 설치 상태는 아래 후속 검증 기록에 구분해 남긴다.
단위/호스트 HTTPS 시험으로 실제 Pi의 초기 설정·영상 성공을
대신하지 않는다. 이번 작업은 신규 CVE 전수 검사 결과가 아니다.

상위 layer의 `0005-dhcp-setup-and-optional-management-ip-policy.patch`를
`camera-firmware`, `camera-firmware-web`, `rpi-cam-hailo-devrepo`에 함께 적용한다.
기존 웹 의존성 보안 패치는 유지한다. 검증 로그는 상위 저장소의 Git 제외 경로
`.state/dhcp-setup-2026-10-11/`에 보관한다.

### 이미지 검증

Hailo 카메라 이미지 `20261011T073859Z-e664cb9647e7`의 Yocto 빌드가 통과했다.
총 7,768개 작업 중 7,695개를 재사용했으며 보고된 경고/오류는 없었다. QEMU
이미지는 빌드하지 않았다. 최종 코드 형식 정리 후 보안 시험 345개도 다시 통과했다.

앱·웹·개발 저장소 레시피 각각의 변경 파일 38개가 검토한 소스와 바이트 단위로
일치한다. 최종 rootfs에서 새 앱/웹 정책 코드, 개발 저장소 변경 파일, 빌드 ID,
서비스 활성화와 서명 공개키를 확인했다. 활성 `app.yaml`, 장비 TLS 개인키,
Codex 로그인 파일은 일반 이미지에 포함하지 않는다.

산출물은 상위 저장소
`artifacts/20261011T073859Z-e664cb9647e7/rpi5-camera-hailo/`에 수집했다.
WIC 압축 이미지·bmap·공개키의 SHA-256 검증과 `scripts/install-ssd.sh --check`가
통과했다. 검사에서 등록 SSD `/dev/sdb`를 식별했으며 마운트·쓰기는 수행하지 않았다.
이 이미지 수집 후 현재 호스트의 Git 제외 `device.json`도 `public_host: null`로
전환했다. 기존 서명 키는 유지했다. 이 설정은 **다음 설치**부터 적용된다.

연결된 SSD는 변경하지 않았으며 실제 Pi에서 새 초기 설정·로그인·영상 재검증은
미실시다. 이 호스트의 `sudo`는 운영자 암호 입력을 요구한다. 전체 이미지 설치는
기존 파일시스템을 지우므로, 기존 계정 보존이 필요한 장비에서 DB 이전과 전체
SSD 재설치를 혼동하지 않는다.
